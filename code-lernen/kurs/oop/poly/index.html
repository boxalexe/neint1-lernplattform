Polymorphie, abstrakte Klassen und Schnittstellen

Ziel dieser Lektion

Du modellierst erweiterbare Software mit Schnittstellen («interface») und abstrakten Klassen, liest Realisierung und Abhängigkeit im UML und begründest, warum Polymorphie if-Ketten ersetzt.

Szenario: Onlineshop

Ein kleiner Onlineshop für IT-Zubehör: Artikel mit Preis und Lagerbestand, ein Warenkorb, Rabatte und Versandkosten. Ab 50 Euro ist der Versand kostenlos.

Der Stoff

Ein Aufruf, viele Klassen – ohne if-Kette

Im Checkout unseres Onlineshops zahlen Kunden per PayPal, Kreditkarte oder Rechnung. Jede Zahlungsart berechnet ihre Gebühr anders. Wenn der Warenkorb jede Zahlungsart per if (art.equals("PayPal")) ... else if ... unterscheidet, muss er bei jeder neuen Zahlungsart (z. B. Apple Pay) umgebaut werden.

Die Lösung ist Polymorphie über eine Schnittstelle (Interface): Zahlungsmethode legt als Vertrag fest, welche Methoden jede Zahlungsart anbieten muss (gebuehrInCent, name), aber nicht wie. Der Warenkorb kennt nur das Interface – kommt morgen eine neue Zahlungsart dazu, entsteht einfach eine neue Klasse, am Warenkorb ändert sich keine einzige Zeile.

Interface, Realisierung und Abhängigkeit im UML

«interface» über dem Namen kennzeichnet die Schnittstelle. Gestrichelte Linie mit hohlem Dreieck (..|>) heißt Realisierung: Die Klasse erfüllt den Vertrag. Gestrichelter offener Pfeil (..>) heißt Abhängigkeit: Warenkorb nutzt nur die Schnittstelle als Parameter.

Wann eine abstrakte Klasse statt eines Interfaces?

Manchmal teilen Unterklassen nicht nur denselben Methodenkopf, sondern auch gemeinsame Attribute und fertigen Code. Beispiel im Shop: Jede RabattRegel hat eine Beschreibung (bezeichnung), aber jede Unterklasse (ProzentRabatt, GutscheinRabatt) rechnet den Abzug anders. Eine „allgemeine RabattRegel“ ohne konkrete Rechenart ergibt als Objekt keinen Sinn.

Deshalb macht man RabattRegel zu einer abstrakten Klasse: Aus ihr darf kein new RabattRegel() erzeugt werden, und ihre abstrakte Methode abzugInCent() hat keinen Rumpf – jede Unterklasse muss sie ausfüllen.

Abstrakte Klasse im UML

Im UML stehen abstrakte Klassen und abstrakte Methoden kursiv (oder mit {abstract}). Die Vererbung ist wieder eine durchgezogene Linie (--|>).

In der Praxis

In Java-Frameworks (Spring, Jakarta EE) werden fast alle Dienste über Interfaces entkoppelt: Im Betrieb läuft der echte Zahlungsdienst, im Unit-Test eine Attrappe mit demselben Interface.

Typische Stolperfallen

Achtung

Weder aus einer abstrakten Klasse noch aus einem Interface kannst du ein Objekt erzeugen. Im Code entsteht immer ein Objekt einer konkreten Klasse (new PayPal()).

Tipp

In IHK-Klassendiagrammen listet die realisierende Klasse die umgesetzten Interface-Methoden erneut in ihrem Methodenfach auf.

Prüfe dich

  1. Was ist der wichtigste Architektur-Vorteil, wenn Warenkorb nur das Interface Zahlungsmethode kennt?
    • Der Warenkorb erbt automatisch alle Attribute von PayPal
    • Neue Zahlungsarten kommen hinzu, ohne den Warenkorb zu ändern
    • Die Berechnung der Gebühren läuft dadurch doppelt so schnell
    • Die Zahlungsarten brauchen dann keine eigenen Methoden mehr
  2. Welche UML-Linie bedeutet „Klasse realisiert ein Interface“ (implements)?
    • Gestrichelte Linie mit hohler Dreiecksspitze
    • Gestrichelte Linie mit offener Pfeilspitze
    • Durchgezogene Linie mit hohler Dreiecksspitze
    • Durchgezogene Linie mit leerer Raute
  3. Woran erkennst du im UML-Klassendiagramm eine abstrakte Klasse?
    • Der Klassenname steht kursiv (oder trägt {abstract})
    • Die Klasse besitzt ausschließlich statische Methoden
    • Über dem Namen steht zwingend das Stereotyp «interface»
    • Der Klassenname ist durchgehend unterstrichen
  4. Wann ist eine abstrakte Klasse besser als ein Interface?
    • Wenn die Klasse keine Unterklassen bekommen darf
    • Wenn eine Klasse drei verschiedene Verträge gleichzeitig erfüllen soll
    • Wenn aus der Vorlage direkt eigene Objekte erzeugt werden sollen
    • Wenn Unterklassen gemeinsame Attribute und fertige Methoden teilen
