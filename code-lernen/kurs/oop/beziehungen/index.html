Beziehungen und Multiplizitäten: UML und Code abgleichen

Ziel dieser Lektion

Du unterscheidest Assoziation, Aggregation, Komposition und Abhängigkeit, liest Multiplizitäten sicher und erkennst im Code sofort, welche UML-Beziehung dahintersteckt.

Szenario: IT-Ticketsystem

Ein Service-Desk: Störungen kommen als Tickets mit Priorität (1 = kritisch bis 4 = niedrig) und Status (offen, in Arbeit, erledigt) und werden Technikern zugewiesen.

Der Stoff

Linien sind Referenzen im Code

In UML-Prüfungsaufgaben steht fast immer ein Klassendiagramm mit verschiedenen Linien und Zahlen. Das Geheimnis: Jede Beziehung im Diagramm entspricht einer ganz bestimmten Stelle im Code. Wer diese Übersetzung kennt, kann Diagramme in beide Richtungen lesen – vom UML zum Code und vom Code zurück ins UML.

Die vier Beziehungen: UML direkt neben dem Code

BeziehungUML-LinieBedeutungWoran erkennst du es im Code?
Assoziationdurchgezogen (-->)„kennt“, „arbeitet mit“Attribut hält Referenz auf anderes Objekt (private Techniker bearbeiter;)
Aggregationleere Raute (o--) am Ganzen„besteht aus“, Teile leben allein weiterFertige Objekte werden von außen übergeben und in einer Liste gesammelt
Kompositiongefüllte Raute (*--) am Ganzen„besteht aus“, Teile sterben mit dem GanzenDas Ganze erzeugt seine Teile selbst (new Position(...)) und gibt sie nicht weg
Abhängigkeitgestrichelt (..>)„nutzt vorübergehend“Andere Klasse taucht nur als Methodenparameter oder lokale Variable auf, nicht als Attribut

Alle Beziehungen im IT-Ticketsystem

Lies jede Linie mit ihren Zahlen: Eine Abteilung umfasst mindestens einen Techniker (1..*, Aggregation: wechselt der Techniker das Team, existiert er weiter). Ein Ticket hat höchstens einen Techniker (0..1, anfangs null), ein Techniker kann beliebig viele Tickets haben (*). ExportDienst speichert kein Ticket, er bekommt es nur kurz als Parameter (Abhängigkeit).

Genau daran unterscheidest du in fremdem Code dauerhafte Verbindungen (Attribut = Assoziation) von kurzfristiger Nutzung (Parameter = Abhängigkeit).

In der Praxis

Immer wenn ein Attribut im Code null/None sein darf, ist die Multiplizität im UML 0..1 statt 1 – ein Klassiker für NullPointerExceptions, wenn man es vergisst.

Multiplizitäten sicher übersetzen

Ein offener Pfeil (-->) heißt gerichtete Assoziation: Nur die Klasse am Pfeilanfang hat das Attribut. Zeigt der Pfeil von Ticket zu Techniker, kennt das Ticket seinen Bearbeiter, der Techniker speichert aber keine Ticketliste.

MultiplizitätBedeutungTypisch im Code
1genau eins (Pflicht)Attribut im Konstruktor gesetzt, darf nie null sein
0..1keins oder eins (optional)einzelnes Attribut, darf null/None sein
* (oder 0..*)beliebig viele, auch keinsListe / ArrayList, darf leer sein
1..*mindestens einsListe, die nie leer sein darf
2..5mindestens zwei, höchstens fünfListe mit Längenprüfung im Code

Typische Stolperfallen

Tipp

Im Zweifel zwischen Aggregation (o--) und Komposition (*--): Frage „Überlebt das Teil, wenn das Ganze gelöscht wird?“ Techniker ohne Abteilung: ja (Aggregation). Warenkorb-Position ohne Warenkorb: nein (Komposition).

Gut zu wissen

In relationalen Datenbanken wird eine * zu * (m:n) Beziehung zu einer eigenen Zwischentabelle mit zwei Fremdschlüsseln.

Prüfe dich

  4. Ein offener Pfeil zeigt von Position zu Artikel (Position "*" --> "1" Artikel). Was bedeutet die Pfeilrichtung?
    • Nur Artikel kennt alle Positionen, nicht umgekehrt
    • Artikel verschwindet, sobald die Position gelöscht wird
    • Position erbt Preis und Name von Artikel

  5. Was bedeutet die Multiplizität 0..1 an Ticket "*" --> "0..1" Techniker?
