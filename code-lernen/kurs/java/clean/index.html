Clean Code: lesbar schreiben, was andere lesen müssen

Ziel dieser Lektion

Du erkennst unsauberen Code an Namen, magischen Zahlen, tiefer Verschachtelung, Wiederholungen und zu großen Methoden, kennst die passende Verbesserung und begründest, warum sie den Code wartbarer macht, ohne sein Verhalten zu ändern.

Szenario: Onlineshop

Ein kleiner Onlineshop für IT-Zubehör: Artikel mit Preis und Lagerbestand, ein Warenkorb, Rabatte und Versandkosten. Ab 50 Euro ist der Versand kostenlos.

Der Stoff

Code wird öfter gelesen als geschrieben

Ein Programm ist einmal geschrieben, aber über Jahre gelesen, geändert und erweitert, meist von anderen. Clean Code heißt: so schreiben, dass der nächste Mensch es schnell versteht. Der Computer führt sauberen und unsauberen Code gleich gut aus, der Unterschied zeigt sich erst bei der nächsten Änderung. Unsauberer Code sammelt Technische Schulden: Jede Änderung wird teurer.

Alle Verbesserungen hier ändern das Verhalten nicht. Das ist der Kern von Refactoring: Struktur verbessern, Ergebnis gleich lassen.

Sprechende Namen

Die Einheit im Namen verhindert, dass jemand mit Euro weiterrechnet.

In der Praxis

In Code-Reviews ist „Was bedeutet x?“ die häufigste Frage. Gute Namen ersetzen Kommentare und machen Fehler sichtbar: preisInCent / 100 liest sich sofort als Umrechnung in Euro.

Keine Magic Numbers

// Nachher: benannte Konstanten, einmal definiert

Die Regel hat einen Namen und steht an einer Stelle.

In der Praxis

Steigt die Versandgrenze auf 60 Euro, muss jemand jede 5000 im Code finden, und die 5000 in der Lagerlogik darf er dabei nicht erwischen. Mit einer Konstante ist es eine Zeile.

Ein Muster, das in fast jeder Codebasis auftaucht. Die kurze Form ist nicht nur kürzer, sie lässt auch keinen Platz für einen vertauschten Zweig.

Typische Stolperfallen

Achtung

Refactoring ändert nur die Struktur, nie das Ergebnis. Nach jedem Schritt muss das Programm genau dasselbe tun wie vorher, am besten durch Tests abgesichert.

Tipp

Kommentare sind kein Ersatz für gute Namen. Ein guter Kommentar sagt, warum etwas so ist („Grenze laut Versandvertrag 2026“), nicht, was der Code tut.

Tipp

KISS: Die einfachste Lösung, die funktioniert, ist meist die beste. Clever verschachtelter Code ist schwer zu prüfen.

Prüfe dich

  1. Was ist eine Magic Number?
    • Eine Zahl, die Java automatisch berechnet
    • Eine Zahl mitten im Code ohne erklärenden Namen
    • Eine Konstante mit final und static
    • Eine Zufallszahl aus der Klasse Random
  2. Was macht eine Guard Clause?
    • Sie beendet einen Sonderfall früh mit return
    • Sie fängt eine Exception automatisch ab
    • Sie schützt Attribute mit private
    • Sie prüft am Ende, ob alles stimmt
  3. Was bedeutet DRY?
    • Jede Regel steht an genau einer Stelle
    • Jede Methode hat genau einen Parameter
    • Code wird ohne Kommentare geschrieben
    • Jede Klasse steht in einer eigenen Datei
  4. Was darf sich beim Refactoring ändern?
    • Auch das Ergebnis, wenn es besser ist
    • Nur die Kommentare
    • Nur die Reihenfolge der Ausgaben
    • Nur die Struktur des Codes
