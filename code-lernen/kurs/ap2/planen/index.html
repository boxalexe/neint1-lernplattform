Planen eines Softwareproduktes: Vorgehen, Projekt, Netzplan, Lizenzen, Oberfläche

Ziel dieser Lektion

Du wählst ein Vorgehensmodell und begründest es, erklärst die Begriffe des Projektmanagements, berechnest einen Netzplan mit kritischem Pfad und Puffern, beschreibst Versionsverwaltung und CI/CD, prüfst Open-Source-Lizenzen auf Pflichten und skizzierst eine barrierefreie Oberfläche als Mockup.

Szenario: Onlineshop

Ein kleiner Onlineshop für IT-Zubehör: Artikel mit Preis und Lagerbestand, ein Warenkorb, Rabatte und Versandkosten. Ab 50 Euro ist der Versand kostenlos.

Der Stoff

Was im Prüfungsteil „Planen“ gefragt wird

Der erste AP2-Teil heißt Planen eines Softwareproduktes. Dort steht weniger Code, dafür Projektarbeit: Vorgehensmodell wählen und begründen, Begriffe des Projektmanagements erklären, Stakeholder einschätzen, Termine im Netzplan berechnen, Versionsverwaltung und automatische Auslieferung beschreiben, Lizenzen von Bibliotheken prüfen und eine Oberfläche skizzieren. Die Grundlagen zu Wasserfall, Scrum, Lasten- und Pflichtenheft stehen im Kurs Software planen. Hier kommt, was darüber hinaus gefragt wird. Durchgehendes Beispiel ist ein Kundenportal für unseren Onlineshop.

Vorgehensmodelle: zwei Kategorien, vier Modelle

Prüfungsfragen verlangen oft zuerst die Kategorie und dann ein Modell daraus mit Begründung. Bei „drei Elemente von Scrum“ zählen Rollen, Artefakte und Termine.

Termine im Netzplan berechnen

Ein Netzplan zeigt jeden Vorgang mit Dauer und Vorgängern. In der Vorwärtsrechnung bekommt jeder Vorgang seinen frühesten Anfang (FAZ, das größte FEZ aller Vorgänger) und sein frühestes Ende (FEZ = FAZ + Dauer). In der Rückwärtsrechnung vom Projektende aus das späteste Ende (SEZ, das kleinste SAZ aller Nachfolger) und den spätesten Anfang (SAZ = SEZ − Dauer). Der Gesamtpuffer ist SAZ − FAZ. Vorgänge mit Puffer 0 bilden den kritischen Pfad: Jede Verspätung dort verschiebt das Projektende. Die Zählung beginnt hier bei 0, Tag 3 als Ende bedeutet: Der Nachfolger startet am Tag 3.

Netzplan des Kundenportals

F beginnt erst, wenn D und E fertig sind: FAZ = größtes FEZ = 14. Rückwärts bekommt C sein SEZ vom kleinsten SAZ der Nachfolger. Kritischer Pfad: A, C, D, F mit 17 Tagen. B und E dürfen zusammen 2 Tage rutschen. Im Gantt-Diagramm sind die Vorgänge Balken auf einer Zeitachse, Abhängigkeiten Pfeile, der Puffer ein heller Balkenrest.

Versionsverwaltung und automatische Auslieferung

Versionsverwaltung mit Git speichert jede Änderung mit Autor und Zeit. Typischer Ablauf: einen Branch für die neue Funktion anlegen, dort arbeiten und committen, mit push auf den gemeinsamen Server laden, per Pull Request prüfen lassen, dann in den Hauptzweig mergen. Haben zwei Leute dieselbe Zeile geändert, entsteht ein Merge-Konflikt, den ein Mensch auflöst. Mit pull holt man die Änderungen der anderen.

CI/CD setzt darauf auf: Nach jedem Push baut ein Server die Software automatisch (Continuous Integration), führt alle Tests aus und liefert sie bei Erfolg aus (Continuous Delivery bzw. Deployment). Gegenüber dem Kompilieren und Kopieren von Hand: immer derselbe Ablauf, Fehler fallen nach Minuten statt nach Tagen auf, kein „bei mir lief es aber“.

Ein Feature-Branch von Anfang bis Ende

Shell
1
git switch -c feature/kundenlogin
Neuen Branch anlegen und hineinwechseln.
2
git add src/login.js
Geänderte Datei für den nächsten Commit vormerken.
3
git commit -m "Login mit E-Mail und Passwort"
Stand mit Nachricht speichern, nur lokal.
4
git push -u origin feature/kundenlogin
Branch auf den Server laden. Jetzt startet die CI-Pipeline.
5
git switch main
Zurück in den Hauptzweig …
6
git pull
… und die Änderungen der anderen holen.
7
git merge feature/kundenlogin
Den Login übernehmen. Meist geschieht das über einen Pull Request im Browser.
In der Praxis

Teams arbeiten fast immer so: Niemand schreibt direkt in main, jede Änderung läuft über einen Branch, wird von der Pipeline getestet und von einer zweiten Person gelesen, bevor sie übernommen wird.

Open Source ist nicht gleich frei von Pflichten

Open Source heißt: Der Quellcode ist offen und darf unter den Bedingungen der Lizenz genutzt, verändert und weitergegeben werden. Darf man jede Open-Source-Bibliothek ohne Einschränkung einsetzen? Nein, das Copyleft der GPL kann verlangen, das eigene Produkt offenzulegen. Vorteile: kostenlos, Quellcode prüfbar, große Gemeinschaft. Nachteile: kein garantierter Support, Pflege kann einschlafen, Sicherheitslücken in Abhängigkeiten, Lizenzpflichten müssen geprüft werden.

LizenzartBeispielePflicht beim Einbau in eigene, verkaufte Software
permissivMIT, Apache 2.0, BSDLizenztext und Urheberhinweis mitliefern, sonst kaum Auflagen
schwaches CopyleftLGPL, MPLÄnderungen an der Bibliothek selbst offenlegen. Das eigene Programm darf geschlossen bleiben, wenn es die Bibliothek nur nutzt
starkes CopyleftGPL, AGPLdas ganze abgeleitete Werk bei Weitergabe unter derselben Lizenz samt Quellcode. AGPL gilt schon bei Nutzung über das Netz

In der Praxis

Ein Mockup ist schnell gezeichnet und billig geändert. Fällt dem Kunden am Mockup auf, dass ein Feld fehlt, kostet das Minuten, im fertigen Programm Tage. Auswahllisten und vorgegebene Formate sind nebenbei die beste Vorbeugung gegen schlechte Datenqualität.

Barrierefreiheit: Beispiele je Kriterium

Rechtsgrundlagen in Deutschland: BITV 2.0 für Behörden und das Barrierefreiheitsstärkungsgesetz für viele Angebote der Wirtschaft, technisch beschrieben in den WCAG. Die Grundsätze der Dialoggestaltung nach ISO 9241-110 stehen in der Lektion Software-Ergonomie.
