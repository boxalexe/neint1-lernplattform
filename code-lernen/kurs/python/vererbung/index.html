Vererbung und Polymorphie: Artikelarten und Zahlungsmethoden

Ziel dieser Lektion

Du leitest Klassen ab, rufst mit super() den Konstruktor der Oberklasse auf, überschreibst Methoden, nutzt Polymorphie über eine gemeinsame Schnittstelle und kennst abstrakte Basisklassen (abc) und Duck Typing.

Szenario: Onlineshop

Ein kleiner Onlineshop für IT-Zubehör: Artikel mit Preis und Lagerbestand, ein Warenkorb, Rabatte und Versandkosten. Ab 50 Euro ist der Versand kostenlos.

Der Stoff

Gleiches einmal, Unterschiede gezielt

Der Shop verkauft auch Software-Lizenzen. Eine Lizenz ist ein Artikel mit Name und Preis, nur Versand kostet sie nichts. Statt die Klasse zu kopieren, erbt DigitalArtikel alles von Artikel und ändert nur, was anders ist: Das ist Vererbung. Artikel ist die Oberklasse, DigitalArtikel die Unterklasse. Der Test heißt „ist ein“: Ein digitaler Artikel ist ein Artikel.

In der Praxis

Artikelarten mit gemeinsamer Basis gibt es in jedem Shop: physisch, digital, Gutschein, Abo. Was alle teilen, steht einmal in der Oberklasse, jede Art überschreibt nur ihre Besonderheit.

Vererbung im UML

Der Pfeil mit hohler Spitze zeigt von der Unterklasse zur Oberklasse. In der Unterklasse steht nur, was neu ist oder überschrieben wird.

Polymorphie: ein Aufruf, viele Verhalten

Der Checkout soll Gebühren berechnen, egal ob PayPal, Kreditkarte oder Rechnung. Alle Zahlungsarten haben dieselbe Methode gebuehr_in_cent, jede rechnet anders. Der Checkout ruft sie einfach auf: Das ist Polymorphie. Eine neue Zahlungsart ist eine neue Klasse, der Checkout bleibt unverändert.

Dass jede Zahlungsart die Methode wirklich hat, sichert eine abstrakte Klasse aus dem Modul abc: Von ihr gibt es keine Objekte, und jede Unterklasse muss die mit @abstractmethod markierten Methoden umsetzen.

In der Praxis

Zahlungsanbieter, Versanddienstleister, Exportformate: Wo mehrere Varianten dieselbe Aufgabe erfüllen, steht in Projekten eine gemeinsame Basis. Neue Anbieter kommen dazu, ohne dass der Checkout angefasst wird.

Zwei Wege zur Polymorphie

Duck Typing ist typisch Python: Ein Objekt muss nicht von Zahlungsmethode erben, es reicht, dass es eine passende Methode gebuehr_in_cent hat. Java verlangt dafür ein Interface.

Typische Stolperfallen

Achtung

super().__init__(…) vergessen: Dann fehlen die Attribute der Oberklasse, und der erste Zugriff auf name endet mit einem AttributeError.

Achtung

Python prüft beim Überschreiben keinen Namen. Ein Tippfehler wie versand_incent legt still eine neue Methode an, und die alte läuft weiter. Ab Python 3.12 hilft der Dekorator @override aus typing zusammen mit einem Typprüfer.

Tipp

Vererbung nur bei echtem „ist ein“. Ein Warenkorb ist keine Liste, er hat eine Liste. Dann ist ein Attribut richtig, keine Vererbung.

Prüfe dich

  1. office = DigitalArtikel(…). Welche Methode läuft bei office.versand_in_cent()?
    • Beide nacheinander
    • Die aus Artikel
    • Die aus DigitalArtikel
    • Keine, das ist ein Fehler
  2. Was macht super().__init__(name, preis)?
    • Löscht die Attribute der Oberklasse
    • Macht die Klasse abstrakt
    • Ruft den Konstruktor der Oberklasse auf
    • Erzeugt ein zweites Objekt der Oberklasse
  3. Was passiert bei Zahlungsmethode(), wenn sie eine abstrakte Methode hat?
    • Die abstrakte Methode liefert dann None
    • Es entsteht ein leeres Objekt ohne Methoden
    • Python wählt selbst eine passende Unterklasse
    • TypeError: Von ihr gibt es keine Objekte
  4. Was bedeutet Duck Typing?
    • Es zählt, welche Methoden ein Objekt hat
    • Jede Klasse muss von object erben
    • Typen werden beim Start geprüft
    • Objekte werden automatisch kopiert
